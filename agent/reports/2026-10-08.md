## What changed
Fixed a **missed leak** where a stated value was wrongly exempted because the same
number also appears in the exercise statement.

`emma_college/leak.py` (`find_leaks`): the *statement exemption* (which lets a hint
quote the exercise verbatim) was suppressing a match whenever the literal value
occurred in the statement — even when the tutor **stated it as the result**. Now a
value in *result position* (`est 10`, `= 10`) is flagged even if that value is also
a given of the statement. This is the real case of a mean that equals one of the
given data (corpus `stat-01`, "Calcule la moyenne de 8, 12 et 10." → "La moyenne
est 10.").

Added `test_result_position_not_exempted_by_statement` in `tests/test_leak.py`:
asserts the answer is flagged in result position, and that the same value mentioned
mid-sentence in a hint is **not** flagged (guard against over-blocking).

## Open questions / remaining gaps (left for a human, one per change)
Three leaks still missed (all non-digit forms; out of scope today):
- `pct-01` "Soixante euros." — number-word answer with no result marker before it;
  the word path requires a result position, so a bare "Soixante" at sentence start
  is not caught.
- `vol-01` "V = 36π cm³." — the expected answer `36π` does not parse (`parse_answer`
  returns empty; mathcore doesn't accept the unicode `π` character), so there is no
  target scalar to match.
- `en-eq-01` "x is five." — English number word ("five") not in result position.

Question: should the word-answer path (FR/EN) be extended to flag a bare number word
when the whole reply *is* that value, and should `π` be normalized in mathcore? Both
look like safe, additive follow-ups but each changes extraction heuristics — I'd
rather get a go-ahead (and a review-model pass) before touching them.
